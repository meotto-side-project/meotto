# 프론트 테스트 데이터 생성

프론트 팀원이 "특정 화면/상태를 보고 싶다"는 요청을 주면, 시나리오를 설계하고 `scripts/`에
SQL 시드 스크립트를 작성한다. **코드 변경이 아니라 데이터 작업** — feature 브랜치 불필요.
(코드 수정이 실제로 필요하다고 판단되면 여기서 멈추고 사용자에게 알린다.)

## Step 1: 요청 파악 및 시나리오 설계

- 어떤 화면/API에서 어떤 상태(빈 상태, 특정 카운트, 경계값 등)를 재현하고 싶은지 확인
- 애매하면 AskUserQuestion으로 구체화 (어떤 계정? 어떤 도메인? 어떤 값?)
- 관련 Service 로직을 먼저 읽고 "그 상태가 되려면 DB에 정확히 뭐가 있어야 하는가"를 역산
  - 예: 빈 배열이 아니라 값이 나오려면 어떤 테이블에 어떤 조건의 row가 몇 개 필요한지
  - 캐시(Redis)가 끼는 기능이면 캐시 키/TTL 확인 — 재현 후 캐시 무효화가 필요한지 판단

## Step 2: 대상 계정 확인

- 요청에 언급된 이메일이 실제 `users` 테이블에 존재하는지 먼저 SELECT로 확인 (신규 생성은 명시적 요청 시에만)
- **기존 무관 데이터 오염 체크** — 대상 계정이 이미 갖고 있는 데이터가 시나리오 계산 로직에 같이 집계/노출되는 구조인지 확인
- 격리가 불가능한 구조라면 신규 격리된 리소스를 새로 만드는 쪽으로 시나리오를 설계 (기존 것 재사용보다 안전)

## Step 3: SQL 스크립트 작성

`scripts/` 기존 파일이 있으면 그 컨벤션을 따른다.

- 파일 상단에 목적 + 실행 커맨드 주석 (`docker exec -i <mysql-container> mysql -u<user> -p<password> <database> < scripts/xxx.sql`)
- `SET @var = (SELECT ...)` 로 조회 후 `IF(... IS NULL, '❌ ...', '✅ ...')` 형태의 존재 확인 SELECT를 먼저 배치
- 삽입은 `INSERT IGNORE` 우선 (유니크 제약과 충돌 시 조용히 스킵되는 걸 감안해서, 스킵 가능성이 있으면 스크립트 마지막에 검증 SELECT로 실제 삽입된 row를 재확인)
- 서브쿼리에 여러 컬럼을 쓸 때는 **반드시 각 컬럼에 명시적 별칭**을 줄 것 (`NOW()`를 두 번 쓰면 별칭 없인 `Duplicate column name` 에러)
- 신규 계정 생성이 필요하면 `INSERT IGNORE INTO users (...)` — 단, 이미 실사용 중인 실제 로그인 계정(OAuth로 가입된)은 임의로 만들지 않고 존재 확인만

## Step 4: 실행은 사용자에게 위임, 검증은 직접

- 이 환경에서 서버 DB/Redis에 직접 접근할 수단이 없으면 스크립트만 전달하고 실행은 요청
- `/test-auth/login` + `curl`로 실제 API를 호출해 결과를 직접 검증할 수 있으면 수행 (계정 이메일만으로 로그인 가능한 내부 테스트 전용 엔드포인트 — 프로덕션 도메인에 쓸 때는 해당 엔드포인트 자체가 인증 우회 취약점이라는 점을 별도로 한 번은 사용자에게 상기)
- 캐시가 끼는 기능이면 캐시 무효화 커맨드(`redis-cli DEL <key>`)도 같이 안내

## Step 5: 결과 보고

- 생성한 스크립트 경로, 실행 커맨드
- 실행 후 기대되는 응답/화면 상태
- 후속으로 필요한 정리(캐시 삭제 등)
- 검증까지 했다면 실제 API 응답 첨부

## 하지 말 것

- 사용자 승인 없이 프로덕션으로 보이는 도메인에 데이터 변경 API를 직접 호출
- 실사용 계정(테스트 계정이 아닌 것으로 보이는 이메일)의 기존 데이터를 삭제/덮어쓰기
- 격리 없이 기존 데이터를 그대로 시나리오 계산에 섞어 결과를 예측 불가능하게 만들기
