# Spec → Plan + Tasks

대상: $ARGUMENTS

Spec은 사용자가 질문에 답한 내용을 반영할 때만 수정한다. 결과물은 `docs/plans/<spec 파일명>.md` 하나다. 문서 규칙은 `.claude/rules/specs.md`.

## 1. 대상 확인

- `$ARGUMENTS`가 비어 있으면 `docs/specs/README.md`의 목차를 보여 주고 대상을 묻는다.
- 대상 Spec 파일이 없거나 F-ID를 찾지 못하면 멈추고 알린다.
- `docs/plans/<feature>.md`가 이미 있으면 내용을 읽고, 덮어쓰지 말고 "갱신"으로 진행한다. 변경 내용을 먼저 사용자에게 보여 준다.

## 2. Spec 분석 (Agent 호출)

Agent 도구로 `spec-analyst`를 호출한다. Agent는 대화를 볼 수 없으므로 프롬프트에 다음을 넣는다.

- Spec 파일 경로, F-ID 범위
- "출력 형식을 따라 질문 목록을 돌려달라"

결과를 사용자에게 그대로 요약해 보여 준다.

**차단 질문이 있으면 여기서 멈춘다.** 사용자가 답하거나 Spec을 고친 뒤 다시 실행하도록 안내한다. 사용자가 답변을 대화로 주면 그 내용을 Spec 파일에 직접 반영하고(답하지 않은 항목은 건드리지 않는다) Plan의 "결정 사항"에도 기록한다. 수정한 Spec 파일과 변경 내용을 사용자에게 보고한다.

## 2-1. 선행 확인

`spec-analyst`가 보고한 의존성(하드/소프트 분류 포함)마다 선행 상태를 확인한다.

Plan은 설계 문서이므로 **선행 기능이 구현되어 있을 필요는 없다.** 선행 Plan이 있으면 된다 (`draft`도 허용). 구현 여부는 `implement-feature`가 구현 시점에 확인한다.

1. 선행 Plan: `docs/plans/<선행 spec>.md`가 있는지 확인한다. 있으면 그 Plan의 API 계약 표를 그대로 참조하고, "선행 Plan과 가정"에 어느 계약에 기대는지 적는다.
2. 판정:
   - 선행 Plan이 있음 → 통과 (구현 여부와 무관)
   - **하드 의존**의 선행 Plan이 없음 → 아래 선택지를 보여 주고 **사용자가 고를 때까지 멈춘다**
   - **소프트 의존**의 선행 Plan이 없음 → 경고만 하고 진행. Plan의 "선행 Plan과 가정"에 기록한다
   - 코드에 이미 구현된 선행 기능이 있으면 Plan에 "구현됨"으로 적고 실제 코드의 형태를 따른다 (`Grep`으로 확인)

하드 의존의 선행 Plan이 없을 때의 선택지:
- **A. 선행 Plan부터**: 선행 기능에 대해 `/plan-feature`를 먼저 실행하도록 안내하고 끝낸다.
- **B. 가정하고 진행**: 선행 Plan이 아직 없지만 있다고 가정한다. 가정(선행이 제공할 Entity, API, 컴포넌트와 그 형태)을 Plan의 "선행 Plan과 가정"에 모두 적고, 선행 Plan이 생긴 뒤 가정을 재검증하는 Task를 추가한다. 가정한 계약은 선행 Plan의 API 계약과 같아야 하므로, 선행 Plan이 있으면 그것을 그대로 따른다.
- **C. 범위 축소**: 선행 없이 가능한 F-ID만 이번 Plan에 포함한다.

사용자가 선택하기 전에는 Plan을 쓰지 않는다. 선행 판단 근거는 Spec의 `파일:섹션`과 함께 보여 준다.

## 3. Plan 작성

차단 질문이 해소된 후 아래 양식으로 작성한다. 코드베이스를 읽어 현재 존재하는 것(도메인, 컴포넌트, 공통 모듈)을 확인하고 재사용 가능한 것은 Task에 반영한다.

````markdown
# Plan: <기능명>

- Spec: docs/specs/<file>.md
- F-ID: F-xx ~ F-yy
- 상태: draft
- 선행 Plan: (없음 | `<spec 파일명>`(F-xx) 하드 / 소프트 ...)
- Linear 상위 이슈: (미연동)

## 선행 Plan과 가정
| 선행 | 종류(하드/소프트) | 상태 | 이 Plan이 가정하는 것 |
|---|---|---|---|
(없으면 "없음". 선택지 B로 진행했다면 가정을 빠짐없이 적는다)

## 결정 사항
- (분석 단계에서 사용자가 확정한 내용. 없으면 "없음")

## 기술 설계
(구조, 데이터 흐름, 주요 설계 선택과 이유)

## 프론트엔드 범위
- web: ...
- mobile: ...

## 백엔드 범위
- 도메인/패키지: ...

## 데이터 모델 변경 (승인 필요)
| 대상 | 변경 | 비고 |
(없으면 "없음")

## API 계약
| ID | Method | Path | 인증 | Request | Response | 에러(name) | F-ID |
|---|---|---|---|---|---|---|---|

- 공통: 응답 상태코드와 오류 형식은 backend/CLAUDE.md의 "API 응답 표준"을 따른다 (`{ name, message }`).
- 새 필드나 경로는 Spec에 없는 설계이므로 승인 대상이다.

## 구현 순서와 의존성
1. API 계약 표 승인 (여기서부터 BE와 FE가 병렬로 시작한다)
2. 공통 준비 Task
3. BE Task들 ∥ FE Task들(MSW 목)
4. 실서버 연동 확인 Task (BE 완료 후)

## 테스트 전략
- BE: 서비스 단위 테스트 대상
- FE: 컴포넌트(스토리 play), E2E 대상 (AC별로 어떤 테스트가 덮는지 적는다)
- 자동 검증이 불가능해 사람이 확인할 AC

## Tasks
| ID | 제목 | 영역 | F-ID / AC | 담당 | 수정 경로 | 선행 | 검증 방법 | Linear |
|---|---|---|---|---|---|---|---|---|
| T-F10-01 | ... | BE | F-10 AC2 | 미정 | backend/.../friend/** | - | gradlew test | |
| T-F10-02 | ... | FE-web | F-10 AC2 | 미정 | apps/web/.../features/friend/** | 계약 승인 | 수동 확인: MSW 목 | |
````

작성 규칙:
- Task는 한 번에 검증 가능한 크기로 쪼갠다. 영역은 `FE-web`, `FE-mobile`, `BE` 중 하나로 쓰고 섞지 않는다. 웹뷰 기반이라 화면은 기본적으로 웹(`FE-web`)에 두고, 푸시 알림처럼 네이티브가 꼭 필요한 것만 `FE-mobile`로 둔다 (`.claude/rules/frontend.md`). 웹↔네이티브 브리지가 필요하면 메시지 계약 표를 Plan에 넣는다. 두 앱이 같은 API를 쓰면 공유 스키마 패키지(`frontend/packages/shared`) 생성을 별도 Task로 둔다.
- **분할 단위는 F-ID × 영역**이다. F-ID마다 BE Task 1개와 FE Task 1개 이상을 둔다. 여러 사람이 F-ID 범위를 나눠 맡을 수 있도록 한 Task가 여러 F-ID에 걸치지 않게 한다 (같은 F-ID 안에서 쪼갤 필요가 있을 때만 더 쪼갠다).
- **담당** 열은 사용자가 정해 준 사람만 적고, 아니면 `미정`으로 둔다. AI가 임의로 배정하지 않는다. **수정 경로** 열에는 그 Task가 건드리는 디렉터리를 적어 두 사람의 Task가 같은 파일을 고치지 않게 한다.
- 여러 F-ID가 함께 쓰는 코드(공용 컴포넌트, 쿼리 키·엔드포인트 상수, 공유 스키마)는 별도 **공통 준비 Task**(`T-{F-ID}-00`)로 분리하고, 그것을 쓰는 Task의 `선행`에 적는다.
- **FE Task는 BE Task를 선행으로 두지 않는다.** FE는 API 계약 표가 승인되면 시작하고, API가 없으면 MSW 목으로 구현한다 (`.claude/rules/frontend-web.md`). `선행` 열에는 `계약 승인`처럼 쓴다. BE가 끝난 뒤에 할 일은 Plan 마지막의 **`실서버 연동 확인` Task**(영역 FE, `선행` = 해당 BE Task들) 하나에 모은다.
- MSW가 아직 설치되어 있지 않으면 첫 번째 공통 Task로 `MSW 구성`(의존성 추가는 승인 필요)을 둔다.
- 다른 Plan의 Task에 의존하면 `선행` 열에 그 Task ID를 그대로 쓴다 (예: `T-F03-02`). 가정으로 진행하는 경우 "가정 재검증" Task를 마지막에 추가한다.
- 모든 AC는 최소 한 Task에 연결된다. 연결되지 않은 AC가 있으면 표 아래에 나열한다.
- Task ID는 `T-{F-ID 숫자}-{nn}`이며 한 번 부여하면 바꾸지 않는다.
- 검증 방법에는 실제 실행 가능한 명령 또는 "수동 확인: <방법>"을 쓴다. 미설치 도구를 전제로 하지 않는다.
- Spec에 없는 내용을 지어내지 않는다. 필요하지만 Spec에 없는 것은 "제안" 표시와 함께 계약/설계에 넣고 승인 대상임을 밝힌다.

## 4. 마무리

- 파일을 `상태: draft`로 저장한다.
- `docs/plans/README.md`(Plan 인덱스)를 갱신한다. 없으면 만든다. 표 열: Plan, 상태, 선행 Plan(하드/소프트), Linear 상위 이슈. 그 아래에 이 표를 근거로 한 권장 구현 순서를 한 줄로 적는다. 갱신 내용은 사용자에게 보여 준다.
- 사용자에게 요약을 보여 준다: Task 수(FE/BE), 승인 필요 항목(데이터 모델 변경, 새 API), 미해결 질문.
- **`approved`로 바꾸는 것은 사람이다.** 승인 후 `/sync-linear-issues`, `/implement-feature` 순으로 진행하도록 안내한다.
