# 기능 검증 (AC 기준)

대상: $ARGUMENTS

PR의 사람 QA 체크리스트를 만드는 `qa-pr`과 다르다. 이 Skill은 **AC와 계약을 증거로 판정**한다. 코드는 수정하지 않는다.

## 절차

1. `docs/plans/<feature>.md`와 대응 Spec이 있는지 확인한다. 없으면 멈춘다.
2. 기준 브랜치(기본 `origin/main`)와의 변경 파일을 확인한다 (`git diff --stat <기준>...HEAD`). 변경이 없으면 멈추고 알린다.
3. Agent 도구로 `spec-verifier`를 호출한다. 프롬프트에 포함할 것:
   - Plan 경로, Spec 경로, 검증할 F-ID 범위
   - 기준 브랜치, 변경 파일 목록
   - "코드 수정 금지, 미실행 검증은 미검증으로 표기"
4. 결과를 받으면 다음을 직접 확인한다.
   - 보고된 검증 명령 결과가 실제 실행에서 나온 것인지 (명령과 결과가 모두 적혀 있는가)
   - AC마다 대응하는 테스트(이름, 실행 결과)가 있는지. 테스트가 없거나 도구 미설치로 못 돌린 AC는 ✅가 아니라 "미검증"이다.
   - AC 판정에 구현 근거와 검증 근거가 비어 있는 ✅가 없는지. 있으면 ⚠️로 내리고 이유를 적는다.
5. 사용자에게 보고한다.

## 보고

`spec-verifier`의 출력 형식을 그대로 쓰되, 맨 위에 다음을 둔다.

```text
종합: ✅ PR 가능 / ⚠️ 미검증 항목 확인 필요 / ❌ 수정 필요
미검증으로 남은 것: <개수와 이유 요약 (도구 미설치, 수동 확인 필요 등)>
```

## 후속

- ❌ 항목: `/implement-feature <Task>`로 수정하도록 안내한다.
- ❓ 판정 불가: Spec 질문으로 사용자에게 돌려준다. Spec을 임의로 고치지 않는다.
- ⚠️ 항목 중 수동 확인이 필요한 것은 `/qa-pr`에서 체크리스트로 쓸 수 있다.
